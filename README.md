# edu_simulations

Монорепа навчальних симуляцій-ігор. Кожна гра — окремий застосунок, який пояснює
предметну область через наслідки рішень гравця, а не через текстові уроки.

## Що всередині

| Пакет | Призначення |
| --- | --- |
| [apps/portal](apps/portal) | Вітрина: головна сторінка з каталогом усіх ігор за категоріями |
| [apps/vineyard](apps/vineyard) | Піксельна симуляція догляду за виноградником: рік за роком, місяць за місяцем |
| [apps/peppers](apps/peppers) | Піксельна симуляція догляду за гострими перцями на заскленому балконі: перезимівля, підсвітка, ручне запилення |
| [apps/founder](apps/founder) | Піксельна симуляція соло-розробника, який будує SaaS на бутстрапі: валідація, воронка, юніт-економіка, вигорання |
| [apps/sysdesign](apps/sysdesign) | Гра-конструктор архітектури для підготовки до System Design-співбесід: кампанія з інцидентами, довідник, картки, оцінки, mock interview |
| [packages/catalog](packages/catalog) | Реєстр ігор: метадані, категорії, статуси, дев-порти — єдине джерело правди для вітрини й збірки сайту |
| [packages/sim-core](packages/sim-core) | Рушій покрокових симуляцій: стан, фази ходу, детермінований RNG, події, збереження |
| [packages/pixel-ui](packages/pixel-ui) | Піксельний UI-шар: canvas із цілочисельним масштабом, палітра, примітиви малювання, віджети |

## Запуск

```bash
pnpm install
pnpm dev --filter @edu/vineyard    # одна гра
pnpm dev                           # усі застосунки: вітрина :5180, ігри :5181–:5184
pnpm build                         # збірка кожного застосунку окремо
pnpm test                          # тести
```

Потрібен Node ≥ 20 і pnpm. Turborepo кешує результати тасків — повторна збірка
без змін завершується миттєво.

## Збірка сайту

Усі ігри деплояться **одним артефактом**: вітрина лягає в корінь, кожна гра —
у власну підтеку.

```bash
pnpm build:site     # усі застосунки + складання в один dist/
pnpm preview:site   # перевірити зібраний артефакт на :4173
```

```
dist/
  index.html            вітрина
  games/vineyard/       гра
  games/peppers/        гра
  games/founder/        гра
  games/sysdesign/      гра
```

Жодних рерайтів чи SPA-фолбеку: це справжні теки зі справжніми `index.html`.
Кожен застосунок збирається з `base: "./"`, тому артефакт релокабельний —
однаково працює з кореня домену й із підтеки. Конфіг для Vercel — у `vercel.json`;
для іншого хостингу достатньо вказати команду `pnpm build:site` і теку `dist`.

Спільний origin означає спільний `localStorage`, але ключі збережень уже
неймспейсовані (`edu-sim:<гра>` у `packages/sim-core/src/save.js`) — саме тому
цю схему іменування не можна «спрощувати».

## Принцип, спільний для всіх симуляцій

Рушій оперує **ефектами**, а не просто числами. Ефект — це атомарна зміна одного
показника, яка обов'язково несе поле `reason`:

```js
makeEffect({
  target: "vine.woodRipeness",
  delta: 9,
  reason: "Калій пришвидшує перетворення цукрів на крохмаль у пагонах",
});
```

Створити ефект без пояснення технічно неможливо — `makeEffect` кине помилку.
З цього логу будуються **всі** навчальні панелі: розбір ходу, підсумковий звіт,
аналіз пропущених дій. Тому пояснення не може розійтися з реальним розрахунком:
змінюючи число, ви змінюєте його разом із причиною.

## Як додати нову симуляцію

1. Створіть `apps/<id>` з `package.json` (`"name": "@edu/<id>"`), `index.html`
   і `vite.config.js` — за зразком `apps/vineyard`. Тека мусить називатися так само,
   як `id` у реєстрі: з нього ж будується публічний шлях `/games/<id>/`.
2. Додайте залежності `"@edu/sim-core": "workspace:*"` і `"@edu/pixel-ui": "workspace:*"`.
3. Додайте запис у `packages/catalog/src/index.js`: `id`, `dir`, `title`, `subtitle`,
   `category`, `tags`, `status`, `released`, `emoji`, `accent` і **вільний** `devPort`
   (той самий порт пропишіть у `server.port` нового `vite.config.js`). Реєстр
   перевіряє себе на імпорті: дубль `id` чи порту падає з поясненням.
4. Опишіть предметну модель: початковий стан, межі показників (`limits`) і фази ходу.
5. За бажанням — `apps/portal/src/thumbs/<id>.js` із власною мініатюрою 120×45 і
   рядок у `thumbs/index.js`. Без неї гра отримає заглушку у своєму акцентному
   кольорі з емодзі, тож вітрина не «зламається».

Реєструвати щось у `turbo.json` не потрібно — таски `dev`, `build`, `lint`, `test`
вже описані в корені й підхопляться автоматично. Вітрина, збирач `dist/` і вкладки
категорій читають той самий реєстр, тому кроку «не забути дописати ще й тут» немає
за побудовою.

Спільне виносьте в `packages/`, а не в сусідній застосунок: пакети — це те, чим
гри обмінюються, і залежність між двома `apps/*` є помилкою архітектури.
