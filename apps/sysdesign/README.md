# Архітектор систем

Піксельна гра-конструктор для підготовки до System Design-співбесід у технологічних компаніях.

Гравець отримує задачу: трафік, SLO, бюджет, а подекуди й зафіксований зовнішній сервіс. Він збирає архітектуру з компонентів: DNS, CDN, load balancer, кеш, SQL, NoSQL, черги, воркери, rate limiter, WebSocket gateway тощо. Потім запускає годину трафіку з інцидентами і дивиться, де саме система ламається.

```bash
pnpm --filter @edu/sysdesign dev        # :5184
pnpm --filter @edu/sysdesign test       # node:test — модель, прогрес, контент, оцінки, картки
pnpm --filter @edu/sysdesign simulate   # баланс рівнів без браузера
```

## Режими

| Режим | Що всередині |
| --- | --- |
| Кампанія | 15 рівнів у 5 главах: основи → масштабування → дані → надійність → класичні задачі. Зірки: працює / тримає SLO / як на співбесіді |
| Довідник | 48 статей (що це, як працює, trade-offs, цифри, «на співбесіді») і глосарій на ~100 термінів. Відкривається з будь-якого місця: палітри, налаштувань, брифу, розбору |
| Картки | 144 картки (MCQ і flash) з розкладом за Leitner: те, що знаєте, повертається рідше |
| Оцінки | 14 задач back-of-the-envelope з варіантами чисел, допуском і покроковим розбором, плюс шпаргалка latency numbers |
| Співбесіда | 5 задач у форматі 45-хвилинної співбесіди: вимоги → оцінки → API → дані → high-level design у конструкторі → deep dive → підсумок, самооцінка за rubric |

## Структура

```
src/data/      контент без DOM: компоненти, рівні, еталони, інциденти, довідник, картки, оцінки, співбесіди
src/sim/       модель без DOM: граф, компіляція маршрутів, валідація, тік, прогін, вартість, перевірки, зірки
src/progress/  збереження й ремонт прогресу, Leitner, оцінювання чисел, розблокування
src/render/    піксельні іконки й шапка на канві
src/ui/        екрани: хаб, рівень, конструктор (builder/), довідник, картки, оцінки, співбесіда
scripts/simulate.mjs   балансовий прогін усіх рівнів
test/          node:test
```

`src/data` і `src/sim` не торкаються DOM, тож модель повністю запускається під голим node. На цьому стоять тести й балансовий скрипт.

## Модель

Модель аналітична, а не пакетна: вона рахує потоки (req/s) хвилина за хвилиною, 60 хвилин на прогін.

1. **Маршрути.** Граф компілюється в план маршрутів для кожного класу запитів: читання, запис, статика, звіти, з'єднання, атака. Роутери (DNS, LB, gateway) ділять трафік між дочірніми вузлами. Код (app, воркери) викликає кожен тип залежності. Кеш без дочірніх вузлів працює як look-aside (cache-aside).
2. **Завантаження.** ρ = робота / потужність. Запис коштує дорожче за читання, full scan дорожче за пошук за індексом, кожен індекс здорожчує запис. Для app ще враховуються потоки за законом Літтла, тож повільна залежність вичерпує потоки навіть за вільного CPU.
3. **Латентність.** Суміш шляхів «фіксована частина + експонента очікування» (наближення Сакасегави для M/M/c). p99 рахується з суміші, тому при 95% влучань у кеш хвіст задають промахи.
4. **Зворотні зв'язки** (кроки 1–4 повторюються до збіжності):
   - повтори без backoff множать навантаження на того, хто вже падає;
   - circuit breaker (closed / open / half-open) відрізає хвору залежність;
   - черга накопичує backlog і лаг, а воркери обмежують тиск на базу;
   - автоскейлер реагує із затримкою.
5. **Інциденти:** сплеск (з розгоном), відмова інстансів, рестарт кешу, hot key, атака, сплеск легітимних клієнтів, повільна або мертва залежність, відмова AZ чи регіону, додавання вузла (mod N проти consistent hashing), пост зірки, reconnect storm.

Детермінізм: той самий граф, рівень і seed завжди дають ту саму годину. Рівні проганяються з фіксованим seed, тож розбір «чому впало» можна відтворити.

### Що свідомо не моделюється

- Окремі пакети, TCP-вікна, GC-паузи, «шумні сусіди», реальні розподіли латентності, крім експоненти.
- Консистентність даних на рівні окремих записів: є лише лаг реплік, TTL кешу й RPO при failover.
- Безпека, окрім rate limiting: автентифікацію, WAF і шифрування варто обговорювати на співбесіді, але в моделі їх немає.
- Година прогону щільніша за реальне життя: у ній більше відмов, ніж буває за квартал. Тому планки SLO тут нижчі за «чотири дев'ятки» з продакшену.

## Баланс

`scripts/simulate.mjs` проганяє для кожного рівня еталонне й наївне рішення з `src/data/solutions.js` на кількох seed:

- еталон мусить брати 3★ на всіх seed, наївне рішення — не більше 1★;
- кожна альтернатива теж мусить брати 3★;
- бюджет не повинен бути надто щедрим: еталон має витрачати щонайменше половину.

Після будь-якої правки чисел у компонентах чи рівнях запустіть скрипт: якщо рівень став тривіальним або нерозв'язним, скрипт упаде.

## Як додати рівень

1. Додайте id у `src/data/order.js` (позиція визначає порядок і розблокування).
2. Опишіть рівень у `src/data/levels.js`: трафік, SLO, бюджет, палітра, інциденти, перевірки, три підказки, розбір.
3. Додайте еталонне й наївне рішення в `src/data/solutions.js`.
4. `pnpm --filter @edu/sysdesign simulate 10 <id>` і `pnpm --filter @edu/sysdesign test`.
